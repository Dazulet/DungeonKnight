## Week 10: Assignment 10, three enemy types

- **2026-11-10.** I asked Claude Code to check that the Shooter can hit a moving player. It fired only 3 times in 40 seconds and never hit. Its "too close" distance (3.5 m) was too big for my small arena, and it aimed at where I was, not where I was going. We changed the distance to 2.5 m and added aim lead. The aim line still locks 0.25 s before the shot, so a side step can dodge it.
- **2026-11-10.** I asked Claude Code to audit all three enemies for fair combat. The Patroller's hit only checked distance, so it could hit me through the edge of a pillar. Also, no enemy checked if I was on the screen. We added a line-of-sight check before the hit and an on-screen check before every attack.
- **2026-11-10.** In a test, some enemies died without ever seeing me, because I could shoot them from farther than they can see. I asked Claude Code to make enemies react to hits, but without seeing through walls. Now a hit turns the enemy toward the shot, and for 3 seconds it can see farther. Walls still block its sight.
- **2026-11-10.** I found out that all this work was committed in the wrong local project folder (github.com/Nurzhigit08/DungeonKnight), not in my repository. I asked Claude Code to audit both projects first. All asset GUIDs were the same, so we moved the work file by file in 6 stages, without copying any Git history. After each stage we ran the Unity tests again in my project before I made the commit.
- **2026-11-11.** Playtest: two testers, my two younger brothers (two different people), played the game for the first time. Tester 1 won on the first try. Tester 2 won on the first try. Both said the game was too easy, and the target is 2–4 tries. In our tests the enemies often died before they could finish an attack. I asked Claude Code for fair changes. We changed Patroller health 4 → 6, Charger health 5 → 7 and Shooter cooldown 1.8 s → 1.4 s. The wind-ups, warnings and damage did not change. New players have not tested these changes yet.

A broken file is copied to `save.broken.json` and the game starts with defaults. It saves after a win, on every settings change and in `OnApplicationPause(true)`.

## Week 13: Assignment 13, juice pass

- **2026-11-24.** Before any change I asked Claude Code for an audit only. It found that the project used the Built-in pipeline, and URP, Shader Graph and even the Particle System module were not in the project. They were inside my Unity 6.6 install (URP 17.6), so no download was needed. It also found a test leftover: Patroller health was 1 instead of 6 in my working copy. I restored 6 and started the new branch `feature/juice-pass` from `feature/data-and-saves`.
- **2026-11-24.** Before the migration we ran all old tests and took reference screenshots in the Built-in pipeline: 156 Assignment 10 checks and 182 Assignment 11 checks passed. My scenes and prefabs are made by builder scripts, so we did the URP setup in code (`JuiceBuilder.cs`): it creates the URP asset with the 2D Renderer, the Volume profile, the materials and the particle prefabs. "Rebuild Scenes" keeps everything. I chose the 2D Renderer because the game is only sprites. I kept Gamma colour space, so the pixel art keeps its colours. Every sprite now uses the URP Sprite-Unlit material, and the Built-in and URP screenshots look the same.
- **2026-11-24.** Five real Particle Systems: enemy hit, enemy death, player damage, coin pickup and level victory. They are small square pixels (2-3 px), they live 0.12-1.4 s, and they destroy themselves. They are drawn below bolts and enemy alert icons, and the HUD is a screen overlay, so they cannot hide my buttons. The victory confetti uses unscaled time, because the game freezes time on the victory screen. The old flipbook effects stay.
- **2026-11-24.** Hit stop is 0.05 s with timeScale 0. My player shoots every 0.28 s, so a stop on every hit would make the game stutter. It happens only on a kill and when I take damage. It only gives time back if the game is still in the Playing state, so it cannot cancel a pause, the victory screen or game over. Tests pause, restart, reload the scene and disable the script during a hit stop, and time is always correct.
- **2026-11-24.** The white hit flash is a Shader Graph (Sprite Unlit): texture × vertex colour, then a lerp to white by `_FlashAmount`. I extended my old `HitFlash.cs` instead of writing a new system. It sets the value with a MaterialPropertyBlock, so no new material is made on a hit. The vertex colour keeps the red wind-up tint of my enemies. The knight keeps the old red flash, because red reads better as "I was hurt".
- **2026-11-24.** Post-processing: soft Bloom (threshold 0.82, intensity 0.55), a little contrast and saturation, and a weak Vignette (0.3). My old sprite vignette was already 70% dark at the edges, so two vignettes would make the corners too dark. When effects are ON the old sprite vignette is hidden; when they are OFF it comes back, so OFF looks like Assignment 11.
- **2026-11-24.** The pause menu has EFFECTS ON/OFF and FPS ON/OFF. OFF turns off only the new Assignment 13 effects; screen shake on damage, the death puff and the coin sparkle still work. The new save fields are `effectsOff` and `showFps`, both `false` by default, so an old `save.json` without them means "effects ON, FPS hidden". A test loads an old save to check this. The FPS counter is hidden by default. Android limits games to 30 FPS by default, so the counter would never show more; I set the target to 60 FPS to see the real headroom.
- **2026-11-24.** Problems found in testing: the first pause menu had a big empty space and the new buttons almost touched the frame, so I made the panel smaller. In the first test run after the URP import, one Editor screenshot showed some wall tiles with the wrong picture. It did not happen in three more runs, and normal screenshots look right, but I will still check it on my phone. All 87 new checks pass in the Editor, and after the last scene rebuild the old 156 + 182 checks still pass. The agent could not finish the APK: Gradle failed with "Unable to establish loopback connection", and the same Java test failed in its sandboxed terminal, so I build the APK myself from the Unity menu. I added a second menu item for a Development + Profiler build. FPS on a real phone and the connected Profiler are still to do.
- **2026-11-24.** My first Development build in the Unity Editor stopped with "Active Input Handling is set to Both", and a few minutes later the Editor crashed. The log shows two separate events: the build was cancelled cleanly by Unity's Android check, and the crash came later inside Unity's own memory clean-up (`DomainUnloadAutoFree`), with none of my scripts in the stack. So the crash cause is not proven; it looks like an Editor bug after a cancelled build. I asked Claude Code to check which input system the game really uses. With "Both", my code already uses the new Input System (`Keyboard.current`, and `InputSystemUIInputModule` in all three scenes delivers the joystick and shoot touches). So I chose "Input System Package (New)", not "Input Manager (Old)": Old would need new EventSystem modules and an untested code path. After the change, all 156 + 182 + 87 tests pass, and an Android project export (Development + Profiler) finishes with 0 errors.

## Week 12: Assignment 12, sound pass (done after Assignment 13)

- **2026-11-25.** I asked Claude Code to add sound on a new branch `feature/sound-pass`, started from `feature/juice-pass`. The project had no audio and no licensed audio files, so all 21 sound effects and both music loops are original files made by procedural synthesis in Python (`Tools/generate_audio.py`): oscillators, filtered noise and envelopes, no samples from other people. The music loops are rendered "around the loop", so the end joins the start without a click.
- **2026-11-25.** Unity has no public script API to create an AudioMixer, but my scenes and assets are made by builder scripts. `AudioBuilder.cs` creates `GameMixer.mixer` through Unity's own internal editor functions (by reflection): Master > Music > Music Pause, Master > SFX, a Compressor on Master and the snapshots Normal and Paused. The first try crashed because the new mixer had no group view in Unity 6.6, so the builder now adds one first.
- **2026-11-25.** An exposed mixer volume is no longer controlled by snapshots after a script sets it. My MUSIC slider must set the Music volume, and the pause must make music quieter too, so they could not use the same fader. The slider sets the Music group, and the Paused snapshot changes a child group "Music Pause" (-10 dB and a 900 Hz low-pass). Pause sets timeScale to 0, so the mixer uses unscaled time; a test checks that the low-pass really reaches 900 Hz while the game is paused.
- **2026-11-25.** One `GameAudio` object has 12 SFX AudioSources and 2 music sources, and no AudioSource is created per event. Every sound has a voice limit and a minimum interval (a test plays the same hit 40 times in one frame and hears it once). Enemy warning sounds start with the red telegraph and are stopped if the attack is cancelled or the enemy dies. In the Editor tests the warning comes 0.55 s (Patroller), 0.70 s (Shooter) and 0.65 s (Charger) before the attack sound.
- **2026-11-25.** All tests ran in the Unity Editor only. Real speaker volume, clipping on the phone, Android audio latency and the music after the app goes to the background are not tested yet; I must check them on my phone.
